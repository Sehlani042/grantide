# Design

Agent → authenticated request API → policy decision → approval/lease → HTTP executor → upstream.
Operator → browser GUI → separate admin API → configuration, review, revocation and audit.

The executor accepts a service ID, never an arbitrary destination. The operator configures service origins. Canonical absolute ASCII paths only; query values are separate. No redirects or ambient proxies. DNS results are checked at dial time, and the checked IP is dialed directly. Public services require HTTPS; internal HTTP/private targets need per-service opt-in. Credentials are injected only after authorization and omitted from snapshots.

A mutex serializes decisions, lease consumption and configuration mutations. Network I/O runs outside it after final reservation. Revocation blocks future reservations; already-dispatched requests cannot be undone. Configuration changes invalidate pending approvals and leases. Deny wins; other modes rank approval, lease, auto. Ties use agent/path/method specificity and stable ID. Rule expiration causes default deny rather than falling through to a weaker rule.

AES-256-GCM encrypts persistent configuration and a bounded metadata audit using a random key file. Atomic replacement and fsync precede dispatch. Directory/files use 0700/0600. A single-instance lock prevents concurrent writers. Tokens and key files must remain outside agent access; encryption is not an OS isolation boundary. Pending bodies, responses and leases are bounded in process memory and disappear on restart. Only agent token hashes are persisted.

The GUI uses a separate bearer token, same-origin calls, no third-party assets and text-only rendering of untrusted values. Strict CSP and Origin/Host checks protect the local surface. Inputs reject unknown fields and enforce size limits. Demo requests use a fixed demo agent and a fake executor.

Go 1.25+. Primary references checked 2026-09-27: https://pkg.go.dev/net/http#Client, https://pkg.go.dev/crypto/cipher#NewGCM, https://pkg.go.dev/net/netip.

## Credential handoff
A separate bounded in-memory queue holds at most 128 credential requests and eight pending requests per agent. Requests are deduplicated by actor/service/method/path and expire after five minutes or policy expiry, whichever is sooner. Only a configured authenticated service covered by a non-deny rule may be requested. No agent-controlled URL, auth type or secret-entry field is accepted. Status reads/cancellation are actor scoped.

Operator entry uses a separate admin endpoint. Credential persistence, audit and revision advance occur under the engine mutex; failure rolls back state. Saving invalidates pending operations, credential requests and leases, marks the resolved request fulfilled, and never dispatches. The credential is service-wide, not limited to the requesting actor or one operation; subsequent calls are independently authorized. HTTP Basic uses the stored username/password via SetBasicAuth. Both plaintext password and exact Basic encoding are redacted from response bodies; arbitrary upstream transformations remain outside this filter's guarantees. Credential request state is lost on restart.

## Browser login coordination (v0.3)
Operator-configured HTTPS website entries have an agent allowlist and are separate from service execution policies. The bounded in-memory handoff queue binds actor, site, browser/profile, tab and conversation metadata. Human confirmation transitions waiting to verification_required; only the owning agent can report verification against the same target and configured origin. A successful report never invokes the HTTP executor or approves a website action. A mutex and persisted audit serialize transitions; failed persistence leaves the prior status intact. Configuration changes invalidate waiting and verification_required records; both expire after 15 minutes and disappear on restart.

This is a cooperative browser handoff protocol. Grantide cannot observe or lock an external browser and cannot independently prove its authentication state. Existing browser adapters must stop reads while the human is entering secrets and resume only after explicit completion. Keeping login on the original website avoids password collection, brittle password-field selectors and cross-context cookie copying. See docs/BROWSER-HANDOFF.md for the full integration contract.

## Controlled login worker
Website accounts are encrypted with the existing store. Login grants, budgets and revocations persist in encrypted state; browser runs are ephemeral. No-expiry grants use a null expiry, while each worker still has a ten-minute maximum deadline. Grant revision binding makes configuration invalidation survive restart. Any configuration mutation revokes grants and cancels active workers. Consuming a grant persists audit before dispatch; consumption is not refunded on failure. Jobs have a ten-minute ceiling capped by grant expiry and one active worker globally. Operator-only challenge resume is distinct from agent polling. Worker stdout is a narrow validated event protocol; stderr is discarded, child debug environments stripped, raw errors never returned. Passwords travel via stdin, not arguments/environment. Each run uses a fresh nonpersistent Chromium context with no storage-state import/export, trace, HAR or video. Browser closes on completion, cancellation or expiry. No browser endpoint is exposed to the agent.

The CloudCone adapter pins origin and form selectors observed on 2026-09-29. Network requests are limited to adapter-approved page/assets/login routes; write methods are limited to the login endpoint while authenticating. After login, only an optional exact instance overview path is available and extracted fields use a fixed numeric/date vocabulary. A provider layout change fails closed. This is a narrow trusted component boundary, not an OS sandbox or a guarantee against a privileged co-resident agent.

Real authentication markers and the `/cloud` landing page were verified on 2026-09-30. Browser request routing alone cannot enforce every redirect hop. JavaScript navigation still passes through the route policy. CAPTCHA assistance in that live verification came from a separately authorized external browser tool, not a new worker capability. Live inventory extraction remains unverified.

The first redirect guard used `route.fetch`, which sends traffic through Node's TLS stack; this desktop's working Chromium network path did not carry over. A live retry reached a login form with a blank CAPTCHA and expired. The worker now uses Chromium's native request continuation and an attached CDP response-stage pause to fail every HTTP 3xx before browser follow-up. If Chromium emits an initial request-stage pause, it proceeds only for the pinned origin and remains subject to the request router. Local fake-site tests verify no redirect second hop; an unauthenticated live CloudCone page with fake local form inputs displays the CAPTCHA image. Real authentication after this change remains pending.

Unlimited uses are represented by an explicit `unlimited_uses` boolean; remaining zero without that flag still denies. Grant creation accepts `unlimited_uses: true` only with `uses: 0`. A stored account owns `next_login_at` and `login_needs_review`, shared across its grants. Dispatch atomically persists the 60-second next-start time and sets review-required before launching the worker, alongside finite-budget consumption. Verified completion clears review-required in the persisted completion audit. All unsuccessful/interrupted outcomes retain the durable pause, including process crashes before a terminal event. Operator-only `review-login` clears the pause while retaining cooldown; it cannot run while a worker is active. Account form edits cannot overwrite these executor-owned controls. Grant listings project the account controls for agent polling without exposing credentials.

## Chrome extension adapter
`POST /v1/extension-logins` uses the existing login grant and account controls, reserving budget/cooldown/review state before queueing an ephemeral `extension_pending` run. The isolated worker and extension cannot run concurrently. The native host polls metadata, atomically claims a credential once (`extension_claimed`), and reports a bounded terminal event through operator-only routes. Failed audit persistence blocks each transition; a failed completion retains the durable review guard. Runs disappear on restart, while consumed budgets and account retry guards remain.

Chrome launches the Go `extension-host` command through a private per-user manifest whose allowed origin is the exact unpacked extension ID. A private launcher binds that ID and state directory. The host validates native-message framing, action and run ID, reads the local port/operator token itself, uses a no-proxy/no-redirect loopback client, and maps only poll/claim/complete. It returns no bearer token. No cross-origin HTTP exception or all-site permission is added.

The Manifest V3 service worker requests CloudCone host access, scripting, alarms, session storage and native messaging. It uses no cookies/debugger/clipboard/broad tabs permission. It prefers an existing approved tab and injects only fixed form/marker/extractor functions. Credentials are passed as transient scripting arguments; session storage contains only task/tab/phase metadata. A 30-second alarm or popup check drives progress, with tab-load events prompting checks. Existing session markers do not establish account identity; the extension will not claim success for them.

Authentication is the trusted extension's fixed-marker report, not independent Go observation. The ordinary Chrome tab remains open and logged in after success. The extension cannot sandbox provider traffic, prevent other tools/extensions from observing the tab, or undo a claimed secret/submitted request. Revocation stops future claims and actions observed on polling; it does not sign out of CloudCone. See docs/CHROME-EXTENSION.md for setup and evidence.

The later live retries still failed with connection-closed errors even in direct Chromium navigation. The successful public-page diagnostic does not establish stable provider connectivity or a sole failure cause. Local redirect guarantees and live network availability remain separate evidence.

## Console password/session authentication

A separate private 0600 auth record stores PBKDF2-HMAC-SHA256 (600,000 iterations, random 16-byte salt) and hashes of random browser-session tokens. Remembered sessions last 30 days and survive server restarts; session-only cookies last at most 12 hours on the server and do not persist in the browser. Logout removes the session before clearing its cookie. The cookie is HttpOnly, SameSite=Strict, host-only and restricted to `/admin`; it is not a raw password or operator token. Loopback HTTP is retained; no Secure flag can be promised on this HTTP origin. Existing Host/Origin/Sec-Fetch-Site validation gates the new routes. Native/CLI operator bearer authentication remains separate from browser cookies; Agent routes never accept browser cookies.

A local `operator-password` CLI reads only stdin, writes a salted hash and clears browser sessions while the server is stopped. It never changes encrypted provider state, Agent tokens, grants or the native-host operator token. Login attempts are throttled after five failures in one minute; sessions are capped at 32. Auth persistence uses atomic replace and fsync before reporting success. Password/source defaults are never published.

Primary references: https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html and https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html (checked 2026-10-03).

## Local enrollment and approval dispatch

`POST /v1/connections` accepts a client-generated 256-bit bearer credential and a bounded conversation/name/CloudCone target. Only its SHA-256 hash enters encrypted state. This endpoint permits requesting review, not acquiring authority. Operator-only `POST /admin/connections/{id}/decision` chooses the saved account and either one 10-minute use or explicit unlimited/no-expiry use. A single lock and encrypted state save cover identity, grant, budget/retry reservation, approval audit and run reference before the extension can claim. Failures restore the state; duplicate approval fails. Newly enrolled identities are website-only and cannot inherit wildcard HTTP API access. Enrollment does not increment the configuration revision because it adds no authority to existing identities; regular configuration mutations retain their invalidation semantics.

Pending requests are capped at 16, history at 128, one active request per bearer, and expire after 15 minutes. Request inspection requires the originating bearer; admin snapshots omit hashes. `GET /v1/connections/latest` resolves only that identity. Completed extension metadata/filtered results persist encrypted. Active runs are marked interrupted after restart; they are never replayed automatically. Config revision changes invalidate pending approvals. Disabled identities cannot submit or inspect requests.

The Python helper uses the calling CODEX_THREAD_ID to name a private credential file, publishes it atomically via a same-directory hard link, enforces ownership/0600 on Unix, and refuses proxies, redirects and non-loopback origins. Discovery is nonsecret metadata written by `serve`, with an optional override/disable flag for test instances. Thread names are self-asserted local labels, not Codex platform identity attestations. Other programs with the same OS-user access are outside this gateway boundary.

Administrator cookies use a per-instance name because HTTP cookies are not scoped by port; a second local test instance must not overwrite the production console session. Previously issued legacy cookies remain accepted only when their server-side session hash is still valid.
