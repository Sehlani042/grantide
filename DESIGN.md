# Design

Agent → authenticated request API → policy decision → approval/lease → HTTP executor → upstream.
Operator → browser GUI → separate admin API → configuration, review, revocation and audit.

The executor accepts a service ID, never an arbitrary destination. The operator configures service origins. Canonical absolute ASCII paths only; query values are separate. No redirects or ambient proxies. DNS results are checked at dial time, and the checked IP is dialed directly. Public services require HTTPS; internal HTTP/private targets need per-service opt-in. Credentials are injected only after authorization and omitted from snapshots.

A mutex serializes decisions, lease consumption and configuration mutations. Network I/O runs outside it after final reservation. Revocation blocks future reservations; already-dispatched requests cannot be undone. Configuration changes invalidate pending approvals and leases. Deny wins; other modes rank approval, lease, auto. Ties use agent/path/method specificity and stable ID. Rule expiration causes default deny rather than falling through to a weaker rule.

AES-256-GCM encrypts persistent configuration and a bounded metadata audit using a random key file. Atomic replacement and fsync precede dispatch. Directory/files use 0700/0600. A single-instance lock prevents concurrent writers. Tokens and key files must remain outside agent access; encryption is not an OS isolation boundary. Pending bodies, responses and leases are bounded in process memory and disappear on restart. Only agent token hashes are persisted.

The GUI uses a separate bearer token, same-origin calls, no third-party assets and text-only rendering of untrusted values. Strict CSP and Origin/Host checks protect the local surface. Inputs reject unknown fields and enforce size limits. Demo requests use a fixed demo agent and a fake executor.

Go 1.25+. Primary references checked 2026-09-27: https://pkg.go.dev/net/http#Client, https://pkg.go.dev/crypto/cipher#NewGCM, https://pkg.go.dev/net/netip.

## Credential handoff
A separate bounded in-memory queue holds at most 128 credential requests and eight pending requests per agent. Requests are deduplicated by actor/service/method/path and expire after five minutes or policy expiry, whichever is sooner. Only a configured authenticated service covered by a non-deny rule may be requested. No agent-controlled URL, auth type or secret-entry field is accepted. Status reads/cancellation are actor scoped.

Operator entry uses a separate admin endpoint. Credential persistence, audit and revision advance occur under the engine mutex; failure rolls back state. Saving invalidates pending operations, credential requests and leases, marks the resolved request fulfilled, and never dispatches. The credential is service-wide, not limited to the requesting actor or one operation; subsequent calls are independently authorized. HTTP Basic uses the stored username/password via SetBasicAuth. Both plaintext password and exact Basic encoding are redacted from response bodies; arbitrary upstream transformations remain outside this filter's guarantees. Credential request state is lost on restart.

## Browser login coordination (v0.3)
Operator-configured HTTPS website entries have an agent allowlist and are separate from service execution policies. The bounded in-memory handoff queue binds actor, site, browser/profile, tab and conversation metadata. Human confirmation transitions waiting to verification_required; only the owning agent can report verification against the same target and configured origin. A successful report never invokes the HTTP executor or approves a website action. A mutex and persisted audit serialize transitions; failed persistence leaves the prior status intact. Configuration changes invalidate waiting and verification_required records; both expire after 15 minutes and disappear on restart.

This is a cooperative browser handoff protocol. Grantide cannot observe or lock an external browser and cannot independently prove its authentication state. Existing browser adapters must stop reads while the human is entering secrets and resume only after explicit completion. Keeping login on the original website avoids password collection, brittle password-field selectors and cross-context cookie copying. See docs/BROWSER-HANDOFF.md for the full integration contract.

## Controlled login worker
Website accounts are encrypted with the existing store. Login grants, budgets and revocations persist in encrypted state; browser runs are ephemeral. No-expiry grants use a null expiry, while each worker still has a ten-minute maximum deadline. Grant revision binding makes configuration invalidation survive restart. Any configuration mutation revokes grants and cancels active workers. Consuming a grant persists audit before dispatch; consumption is not refunded on failure. Jobs have a ten-minute ceiling capped by grant expiry and one active worker globally. Operator-only challenge resume is distinct from agent polling. Worker stdout is a narrow validated event protocol; stderr is discarded, child debug environments stripped, raw errors never returned. Passwords travel via stdin, not arguments/environment. Each run uses a fresh nonpersistent Chromium context with no storage-state import/export, trace, HAR or video. Browser closes on completion, cancellation or expiry. No browser endpoint is exposed to the agent.

The CloudCone adapter pins origin and form selectors observed on 2026-09-29. Network requests are limited to adapter-approved page/assets/login routes; write methods are limited to the login endpoint while authenticating. After login, only an optional exact instance overview path is available and extracted fields use a fixed numeric/date vocabulary. A provider layout change fails closed. This is a narrow trusted component boundary, not an OS sandbox or a guarantee against a privileged co-resident agent.

Real authentication markers and the `/cloud` landing page were verified on 2026-09-30. HTTP dispatch disables automatic redirect following and aborts every 3xx response before returning it to the browser; routing alone cannot enforce every redirect hop. JavaScript navigation still passes through the route policy. CAPTCHA assistance in that live verification came from a separately authorized external browser tool, not a new worker capability. Live inventory extraction remains unverified.

Unlimited uses are represented by an explicit `unlimited_uses` boolean; remaining zero without that flag still denies. Grant creation accepts `unlimited_uses: true` only with `uses: 0`. A stored account owns `next_login_at` and `login_needs_review`, shared across its grants. Dispatch atomically persists the 60-second next-start time and sets review-required before launching the worker, alongside finite-budget consumption. Verified completion clears review-required in the persisted completion audit. All unsuccessful/interrupted outcomes retain the durable pause, including process crashes before a terminal event. Operator-only `review-login` clears the pause while retaining cooldown; it cannot run while a worker is active. Account form edits cannot overwrite these executor-owned controls. Grant listings project the account controls for agent polling without exposing credentials.
